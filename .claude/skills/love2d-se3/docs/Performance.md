## 1. Стоимость стандартного обхода дерева

Каждый кадр — три прохода по всему дереву (пока живо `state == "active"`):

- `scene:__update(dt)` — каждый узел может выполнить свой `update`.
- `scene:__draw()` — каждый узел рисуется (либо через `__draw` напрямую, либо через `SGroup` с `cacheCoords` + `drawCached`).
- События — при каждом `love.mousemoved`/etc делается ещё один обход.

Счётчик, который стоит держать в голове: **сколько узлов в дереве?**

| Узлов | Комфортно |
|-------|-----------|
| 50–200 | нормально, не задумываясь |
| 200–1000 | следить за `update` — избегать тяжёлой логики |
| 1000–5000 | оптимизация: SCanvas, пулы, флаги `off` на невидимых группах |
| >5000 | пересматривать архитектуру: partial tree, ручной batching |

### Дешевые операции в обходе

- `SObject:transform` — арифметика, несколько `math.cos/sin`. Дешево.
- `SObject:__draw` без собственного `self:draw` (узел-контейнер) — только рекурсия. Дешево.
- Проверка `if not c.off and c.__draw then` — Lua table lookup. Дёшево.

### Дорогие операции

- `self:draw` для `SSprite` с большим числом спрайтов — **не** сам draw, но `love.graphics.setColor` / `love.graphics.draw` через драйвер. Десятки тысяч в кадр — OK, сотни тысяч — уже тупит.
- `SGroup` с z-сортировкой — `lume.sort` на каждом `add`/`setZ`. **Не** каждый кадр; только при изменениях. См. [§4](#4-z-сортировка).
- Ваш `update(dt)` — зависит от вас.

### Правило

**Не кладите тяжёлую логику в `update`, если можно — в обработчик события.** Таймер, который каждый кадр спрашивает Love о чём-то сложном, — анти-паттерн. Считайте на событии, сохраняйте результат.

## 2. Атласы vs отдельные картинки

### Правило №1: атласы

Атлас — одна текстура, много квадов. `love.graphics.draw(atlas_img, quad, ...)` для всех спрайтов из одного атласа батчится драйвером Love в 1 draw-call на текстуру.

Отдельные PNG — каждая отдельная `love.Image`. Каждая отрисовка — отдельный draw-call (или так, но переключение текстуры ломает батчинг).

```
сцена из 50 спрайтов:
  все из одного атласа  → ~1 draw-call
  все отдельные PNG     → ~50 draw-calls
```

Разница — огромна на слабых машинах. Всегда упаковывайте спрайты в атласы через TexturePacker.

### Когда отдельные картинки ОК

- Большие фоны (1920×1080), которые в атлас не влезут без огромного атласа.
- Спрайты, используемые один-два раза за всю игру.
- Динамически генерируемые `love.Canvas` — их нельзя запихнуть в атлас.

### `resource:get(name)` дёшев

Поиск по имени — hash lookup. Не переживайте:

```lua
-- это норма в цикле:
for i = 1, 100 do
  love.graphics.draw(resource:get("sprite_" .. i))
end
```

Дорого только `newImage`/`newQuad` — а SE3 загружает их один раз через `SLoader`.

## 3. SCanvas — когда кэш окупается

`SCanvas` первым кадром рендерит дерево в offscreen-буфер, дальше — рисует этот буфер.

### Окупается, если:

- Поддерево **не меняется** кадр в кадр (или меняется редко).
- Поддерево содержит **много** узлов (десятки-сотни).
- Поддерево вызывает **дорогие** операции (шейдеры, много draw-calls).

### Не окупается, если:

- Поддерево небольшое (10-30 узлов) — прямой рендер дешевле, чем память под canvas + blit.
- Поддерево анимируется — кэш сбрасывается каждый кадр через `:refresh()`.
- Вам нужна z-сортировка внутри — кэш не поддерживает; все дети «замораживаются».

### Пример: статический HUD

HUD с score, health-bar, карта — статические элементы, которые обновляются редко:

```lua
local hud = SCanvas{
  canvasSize = { 400, 1080 },
  children = {
    SSprite{ img = "hud_bg" },
    HealthBar{ id = "hp", y = 100 },
    MiniMap{ y = 300 },
    SText{ font = "main", id = "score", text = "0" },
  }
}

-- Когда что-то изменилось — сбросить кэш:
hud:byId("hp"):setValue(newHp)
hud:refresh()   -- автоматически в setValue; но если меняли напрямую — дёрните
```

Canvas перерендерится **только** если `:refresh()` был вызван. Если HUD обновляется 5 раз в секунду, а игра — 60 FPS, экономится 55 перерисовок HUD.

### Важно: `refresh` рекурсивно поднимается

```lua
self._bar:setValue(...)  → :refresh() → parent → parent → SCanvas
```

`SCanvas.refresh` сбрасывает флаг кэша. Это работает автоматически, если ваши методы используют `:refresh()` для любых визуальных изменений.

Если пишете значение напрямую (`sprite.color = {...}`), кэш **не** сбросится. Используйте `setColor` или вызовите `:refresh()` вручную.

## 4. Z-сортировка

`SGroup` пересортировывает `zchilds` при каждом `add` или `setZ`:

```lua
function SGroup:zrefresh(obj)
  if lume.find(self.zchilds, obj) == nil then
    lume.push(self.zchilds, obj)
  end
  self.zchilds = lume.sort(self.zchilds, function(a,b) return a.z > b.z end)
end
```

`lume.sort` = `table.sort` = `O(n log n)` в среднем. Для 100 детей — ~700 сравнений.

### Дорого, если:

- Каждый кадр меняете `z` у многих детей.
- Динамически добавляете/удаляете детей каждый кадр.

### Не дорого, если:

- Дети с фиксированным `z` (добавили — забыли).
- Редко меняете z-порядок (раз в секунду-две).

### Оптимизация: «не пересортировывать каждый раз»

Если каждый кадр вы меняете `z` у 50 спрайтов, сортировка на каждом изменении — расточительна. Паттерн — пакетное обновление:

```lua
-- Плохо:
for i, enemy in ipairs(enemies) do
  enemy:setZ(newZFor(i))   -- 50 сортировок
end

-- Хорошо:
for i, enemy in ipairs(enemies) do
  enemy.z = newZFor(i)       -- прямая запись, без :setZ
end
parent.zchilds = lume.sort(parent.zchilds, function(a,b) return a.z > b.z end)
```

Минус — коплируется знание про `zchilds` в вашем коде. Делайте это только если профилировщик показывает проблему.

## 5. Текст

`love.graphics.printf` — самая дорогая операция в типичной UI-сцене, после шейдеров.

### Фиксированный текст — считайте один раз

```lua
-- Плохо: каждый кадр пересчитывает metrics
function HUD:draw()
  local w = font:getWidth(self.scoreText)    -- дорого, если scoreText не меняется
  ...
end

-- Хорошо: SText делает это сам, в setText
-- HUD просто добавляет SText с нужным text, и он кэширует w
```

`SText:setText(s)` считает `font:getWidth(s)` один раз и сохраняет в `self.w`. Если вы не меняете `text` — пересчёта нет.

### `maxWidth` и `getWrap` — дороже обычного измерения

`SText` с `maxWidth` делает `font:getWrap(text, maxWidth)` — полный перенос по словам. Не катастрофа, но избегайте вызывать `setText` каждый кадр с новой строкой, если можно.

### Большие шрифты — большая текстура

Love создаёт текстуру atlas для каждого шрифта. Размер шрифта 64 → заметная VRAM. Если есть и `size 32`, и `size 64`, и `size 128`, помнить — это три отдельных текстуры.

Оптимизация: держите 2-3 размера (main, small, tiny), масштабируйте для экзотических случаев через `sx/sy` (потеряете чёткость, но сэкономите память).

### Canvas для статического текста

Если на экране куча неизменяемых надписей (лор-текст, subtitle-блок):

```lua
local textBlock = SCanvas{
  canvasSize = {800, 400},
  children = {
    SText{ font = "main", text = "...", maxWidth = 780 },
  }
}
```

Printf случится один раз в canvas, дальше — просто blit. Для больших блоков статического текста — заметная разница.

## 6. Шейдеры

Шейдер — самая дорогая операция в типичной сцене.

### Стоимость

- `setShader` / `unsetShader` — switch, ~несколько μs.
- Проход через фрагментный шейдер — **за каждый пиксель**. Full-screen fragment shader на 1080p = ~2 млн fragments.
- Сложные шейдеры (blur, bloom) с несколькими `Texel` вызовами — тяжелее в разы.

### Паттерны

- **Шейдер на маленьком поддереве** — дёшево. Glow на иконке, tint на одной кнопке.
- **Шейдер на всю сцену** — может потянуть. Для пост-эффектов используйте `SCanvas` + `SShader` — сначала рендер в буфер, потом один проход через шейдер.
- **Многопроходные эффекты (gaussian blur)** — два `SCanvas` попарно: вертикальный проход, потом горизонтальный. Стандартный приём Love.

### Динамические параметры

```lua
shader:send("time", elapsed)
```

Сам `send` — быстрый. Но шейдеру теперь нельзя батчить с другими — граница рендера. Минимизируйте число разных шейдеров на экран.

## 7. События

`__mousemoved` вызывается **каждый кадр** (если курсор двигается). Для 100-узловой сцены — 100 вызовов `__mousemoved` и столько же `inBox` тестов.

### Не дорого

AABB `inBox` — 4 сравнения. Для 1000 узлов — 4000 сравнений. Не проблема.

### Может быть дорого

- `transformMouse` делает несколько `math.cos/sin/sqrt`. На 1000 узлов — OK; на 10000 — уже заметно.
- Кастомный `inBox` с пиксельным тестом — дорого, избегайте.

### `eventoff` экономит обход

Декоративные оверлеи, debug-панели, любые поддеревья, **не** нуждающиеся в событиях:

```lua
{ type = "SGroup", eventoff = true, children = {
  decorative subtree...
}}
```

Весь поддрево исключается из event-прохода. Экономит цикл `for` + вызовы функций.

## 8. Память и выгрузка ассетов

### Основные потребители

- Атласные текстуры. 2048×2048 RGBA = 16 MB VRAM.
- Стримовые звуки (буферы).
- Canvas-ы для рендера-в-текстуру.

### Выгрузка при переключении сцены

`SESceneManager` автоматически вызывает `SEEnvironment:setLoader(new, "scene")`, который делает `unload` на предыдущем scene-loader-е и `collectgarbage("step", 200)`.

Это работает **только если** вы не держите прямые ссылки на love-объекты из предыдущей сцены. Проверьте:

```lua
-- Плохо: держим love.Image после смены сцены
GameState.heroImage = resource:get("hero")   -- ссылка останется после unload!
```

Решение — держите **имя** ассета, не объект:

```lua
GameState.heroImageName = "hero"
-- В месте отрисовки:
resource:get(GameState.heroImageName)   -- работает, когда сцена активна
```

### Ручной `collectgarbage`

По умолчанию Lua GC работает автоматически. Если вы видите «дёргания» при выгрузке сцены, вставьте:

```lua
collectgarbage("collect")
```

после ключевых моментов (например, сразу после `manager:change`). Жёсткий GC один раз за сценой — приемлемо; каждый кадр — **нет** (сильно просаживает FPS).

## 9. Love-специфичные оптимизации

### `love.graphics.setColor(1,1,1)` перед draw

SE3 и Love 11+ используют общий диапазон `0..1`. Защитный приём — всегда возвращать белый после своего `setColor`, чтобы следующий `love.graphics.draw` не утащил ваш тинт:

```lua
function MyClass:draw(x, y, r, sx, sy)
  if self.color then love.graphics.setColor(self.color) end
  love.graphics.draw(img, x, y, r, sx, sy)
  if self.color then love.graphics.setColor(1, 1, 1, 1) end
end
```

Все встроенные SSprite-классы это делают. Дополнительно `SESceneManager:draw` снапшотит и восстанавливает `love.graphics.getColor()` вокруг сценного draw — сырой Love2D-код снаружи движка не может «утечь» цветом внутрь сцены и наоборот.

### VSync

Если сцена на 60 FPS кажется сложной — проверьте, включён ли vsync:

```lua
-- conf.lua
t.window.vsync = 1   -- по умолчанию
```

Выключение `vsync = 0` даёт «ничем не ограниченный» FPS, что полезно при профилировании (видно реальную стоимость).

### Многопоточность

Love поддерживает `love.thread`. Для тяжёлой I/O-обработки (загрузка ассетов) — вынесите в поток. SE3 из коробки не использует — `SLoader:step()` блокирующий. Если нужен прогресс-бар без единого джиттера — потоковый лоадер над SE3 уже проект в себе.

## 10. Профилирование

### `love.timer.getAverageDelta`

```lua
function love.draw()
  ...
  love.graphics.print(("FPS: %d (%.2f ms)"):format(
    love.timer.getFPS(),
    love.timer.getAverageDelta() * 1000
  ), 10, 10)
end
```

Покажет текущий FPS и среднее время кадра в мс. Цель — ≤ 16.7 ms для 60 FPS.

### Stats

```lua
local stats = love.graphics.getStats()
-- stats.drawcalls    — сколько draw-ов за кадр
-- stats.canvasswitches — сколько переключений canvas (дорого)
-- stats.texturememory  — VRAM, использованная текстурами
-- stats.images, stats.canvases, stats.fonts — счётчики
```

Рисуйте их на экране в dev-режиме:

```lua
function love.draw()
  scene:__draw()
  if DEBUG then
    local s = love.graphics.getStats()
    love.graphics.print(("draws:%d swtch:%d mem:%dMB"):format(
      s.drawcalls, s.canvasswitches, s.texturememory / 1024 / 1024), 10, 30)
  end
end
```

Цель — держать `drawcalls` в разумных числах. Для UI — 50-200 за кадр. Для геймплея с эффектами — 200-500. Выше 1000 — пора оптимизировать (больше атласов, меньше переключений шейдеров, batching).

### Lua-профайлер

Для «какая функция съедает FPS» — используйте [jprof](https://github.com/pfirsich/jprof) или ручную инструментацию:

```lua
local t = love.timer.getTime()
heavyOperation()
print(("heavyOp: %.2fms"):format((love.timer.getTime() - t) * 1000))
```

Не оптимизируйте вслепую. Измерьте — увидите, что 90% времени уходит на одну функцию, и остальное не важно.

### Counter узлов

Самое первое, что стоит проверить:

```lua
local function countNodes(node)
  local n = 1
  for _, c in ipairs(node.childs or {}) do n = n + countNodes(c) end
  return n
end

print("tree size:", countNodes(scene))
```

Если у вас 3000 узлов и FPS падает — это нормально, оптимизируйте число узлов, не код. Если 50 узлов и падает — ищите hot-функцию.

## Итого: список первой помощи

Когда сцена тормозит, попробуйте в таком порядке:

1. **Посчитайте узлы.** Много — оптимизируйте их количество, а не код.
2. **Проверьте `love.graphics.getStats().drawcalls`.** Много — объединяйте в атлас или добавляйте `SCanvas`.
3. **Посмотрите на свой `update(dt)`.** Ничего тяжёлого не должно там быть в горячих путях.
4. **Проверьте шейдеры.** Снимите их временно — есть разница? Значит, упирается в шейдер.
5. **`SCanvas` на статическую часть.** Особенно HUD, фон, static UI.
6. **`eventoff` на то, что событиями не интересуется.**
7. **Профайлер.** Если всё выше не помогло — нужна конкретика.

Главное — не оптимизируйте преждевременно. 95% проектов SE3 не упираются в производительность.
